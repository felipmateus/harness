# ADR-002: Unix socket only, served by the standard library

## Status

Accepted

## Date

2026-10-28

## Context

The CLI, and later agents, must reach the daemon.

CompozyOS serves the same handlers over two transports (OBS-API-001…004):
- a Unix socket (mode 0600, no auth middleware);
- HTTP on `localhost:2123`, with Host/Origin checks, app tokens, surface matrices and privileged-mutation guards.

It uses `gin` for routing.

The roadmap puts the web UI and the HTTP surface outside the epic. The user chose macOS and Linux only (2026-10-28), and both have Unix sockets.

## Decision

The daemon listens **only on `<home>/daemon.sock`**, mode 0600, inside a 0700 home. It serves HTTP/1.1 with **`net/http` and the Go 1.22+ `ServeMux` patterns** (`GET /api/streams/{stream}/events`). The socket's file permission is the access-control boundary, and there is no token auth.

The CLI uses an `http.Client` whose transport dials the socket.

## Alternatives Considered

### Alternative 1: UDS + localhost HTTP (Compozy)

- **Description**: both transports, sharing handlers.
- **Pros**: browsers and tools without UDS support can connect; this is the basis for a future web UI.
- **Cons**: a TCP listener is reachable by every local user and by browser pages (DNS rebinding, CSRF), which needs Host/Origin checks and token auth from day one.
- **Why rejected**: no consumer needs TCP before a web UI exists. The transport can be added later behind the same handlers without changing the API shape.

### Alternative 2: gRPC over the socket

- **Description**: typed RPC with generated clients.
- **Pros**: strong typing; streaming built in.
- **Cons**: needs a codegen toolchain; `curl` and agents cannot poke it easily; SSE is simpler for event streams.
- **Why rejected**: JSON over HTTP with SSE is directly scriptable by agents (`curl --unix-socket`), which is a stated goal (US-012).

### Alternative 3: `gin` or another router

- **Description**: a third-party HTTP framework.
- **Pros**: middleware ecosystem; binding helpers.
- **Cons**: an extra dependency; Compozy's mixed strict/lenient binding (62 vs 67 handlers, §5.4 of the reverse spec) shows how framework binding drifts.
- **Why rejected**: the standard library now has method and wildcard routing. Strict JSON decoding is a few lines.

## Consequences

### Positive

- No network exposure; no auth code to get wrong.
- Zero routing dependencies.
- Uniform error shape enforced in one helper.

### Negative

- Browsers cannot connect until an HTTP transport is added.
- The socket path is limited to at most 103 bytes on macOS and 107 on Linux (the `sun_path` buffers are 104 and 108 bytes, including the terminating NUL). Very long `HARNESS_HOME` paths therefore fail fast with `socket_path_too_long`, before anything is spawned.
- The socket's mode protects nothing if others can write the directory that holds it: anyone who can write the home can unlink the socket and bind an impostor. The home must therefore be private. The daemon refuses a symlinked, foreign-owned, or group/other-writable home with `home_insecure` (review-001 F9).

### Risks

- Another process running as the same user can drive the daemon. Accepted: the threat model is a single-user machine, matching Compozy's UDS posture.
- **Go's `UnixListener` may unlink the socket file itself on `Close`.** The design calls `SetUnlinkOnClose(false)` and removes the file at its own shutdown step, so the documented order holds either way (review-001 F3c).

## Implementation Notes

- Before listening, remove a stale socket file **only while holding the daemon lock** (see `_spec.md` Safety Invariants).
- Create the socket with a restrictive umask, then `chmod 0600` before accepting connections.
