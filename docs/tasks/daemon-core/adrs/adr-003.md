# ADR-003: Idiomatic Go architecture, with ports only at real variation edges

## Status

Accepted

## Date

2026-10-28

## Context

The `daemon-core` design organizes code by component (`ledger`, `broker`, `api`, `cli`…). Interfaces are declared by their consumers, and one composition root (`internal/daemon`) wires everything. This is also how CompozyOS is built (`internal/AGENTS.md`: flat packages, interfaces at the consumer, constructors with functional options).

The user compared two alternatives against what the `daemon-core` spec and `docs/roadmap.md` already plan: hexagonal architecture (Ports & Adapters) and Clean Architecture. The review found that the design already honours the dependency rule. `api` depends on interfaces, and `ledger` knows nothing about transport. It also found one structural flaw: the follow algorithm lived inside the HTTP handler, although `loop-engine` (and later `hosted-tools`) will need to follow streams without HTTP.

**User decision (2026-10-28):** adopt neither style wholesale. Use ports only at the ACP and `loop-engine` edges, and extract the follow algorithm as a plain function.

## Decision

1. **Default style: idiomatic Go.**
   - Packages are organized by component.
   - Small interfaces are declared in the package that consumes them.
   - Constructors return concrete types.
   - `internal/daemon` is the only composition root.
   - An architecture test (`internal/archtest`) enforces import direction.
2. **Ports only where variation is real.** A port is an interface with more than one production adapter, or an external boundary that tests must replace. Only two exist in the epic:
   - **Agent runtime** (feature `acp-sessions`): an `AgentRuntime` port, with an ACP-over-stdio adapter (one per provider command) and a fake ACP agent adapter for tests (the Compozy `acpmock` idea).
   - **Action execution** (feature `loop-engine`): an `ActionExecutor` port with a registry keyed by action kind. `run-agent`, built-in actions (`import_tasks`, `write_review_artifacts`, `finalize_review_round` from `spec-cycle-runtime`) and judges (command, built-in) are adapters registered at the composition root.

   The exact signatures belong to those features' specs.
3. **Shared logic is extracted as plain functions, not ports.** The follow algorithm becomes `internal/stream.Follow`, which is transport-agnostic. The SSE handler only frames its output. `loop-engine` will call the same function to watch `session:<id>` streams.
4. **Rule for future ports.** Introduce a port when a second production implementation exists, or when an external process or network boundary must be replaced in tests. Never introduce one speculatively. SQLite, the Unix socket and the in-memory broker stay concrete; tests use the real SQLite.

## Alternatives Considered

### Alternative 1: Full hexagonal (Ports & Adapters everywhere)

- **Description**: a domain package (`event`), use-case packages (`stream`, `lifecycle`) owning ports (`Store`, `Publisher`, `Lock`, `ConfigSource`…), and adapters under `adapters/` (`sqlite`, `broker`, `httpapi`, `fs`, `logging`).
- **Pros**: use cases are testable with in-memory stores; storage and transport become replaceable.
- **Cons**: every port in `daemon-core` would have exactly one implementation; the in-memory store would duplicate SQLite semantics (sequence assignment, idempotency) that are cheaper to test against the real engine.
- **Why rejected**: indirection without a second implementation is speculative (YAGNI). The real variation points are ACP and actions, which come in later features.

### Alternative 2: Clean Architecture, literal layering

- **Description**: `entities/`, `usecases/`, `interfaces/` (controllers, presenters, gateways), `frameworks/`, with DTO↔entity mappers between layers.
- **Pros**: a widely known vocabulary; a strict dependency rule.
- **Cons**: the same speculative ports as Alternative 1, plus mapping layers and generic package names that Go style discourages; heavy for a single-binary local daemon.
- **Why rejected**: ceremony exceeds benefit at this size. The dependency rule is already enforced by the architecture test.

### Alternative 3: No interfaces at all

- **Description**: every package calls concrete types directly.
- **Pros**: least code.
- **Cons**: the ACP agent cannot be faked, so session tests would need a real model; the loop engine would hard-code action kinds, so `spec-cycle-runtime` would have to modify the engine.
- **Why rejected**: it fails the two real variation edges.

## Consequences

### Positive

- `daemon-core` stays small and concrete, and its tests exercise real SQLite and real sockets.
- The two ports that matter are designed where they have several implementations, not guessed up front.
- Follow logic exists once and is reusable by HTTP, the loop engine and future MCP tooling.

### Negative

- Swapping SQLite for another store later would mean refactoring `ledger` callers, not writing an adapter. This is accepted: ADR-001 chose SQLite deliberately.
- Developers used to Clean Architecture will not find layer folders; the architecture test and this ADR are the map.

### Risks

- **Ports appearing ad hoc in later features.** Mitigation: rule 4 above, checked in each feature's spec review.

## Implementation Notes

- `internal/stream` may import `ledger` (types) and `broker` (types). It must not import `api`, `daemon` or `cli`.
- `internal/api` imports `stream` and owns only HTTP and SSE concerns: routing, validation, framing, keepalive, write deadlines.
- Consumers declare the interfaces they use (review-001 F19). `api` defines its own `eventReader`, `statusSource`, `doctorRunner` and `gate` interfaces and receives a follow function. It does not import provider-side interfaces from `ledger`, `broker` or `doctor`. Boundaries are checked on **direct** imports, so a dependency of a dependency does not make a rule ambiguous.
- Roadmap features 2 and 3 carry a note requiring their specs to define `AgentRuntime` and `ActionExecutor`.
