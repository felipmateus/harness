# ADR-001: One SQLite file holding a per-stream event ledger

## Status

Accepted. Amended on 2026-10-28 by review-001 (F1 option A, F14, F24g): full durability, rowid table layout, corrected platform and Compozy notes.

## Date

2026-10-28

## Context

The harness daemon needs a durable, ordered event store. It starts with the daemon's own events. Session events (`acp-sessions`) and loop events (`loop-engine`) will follow.

The reference implementation, CompozyOS v0.4.2, uses three kinds of SQLite database:
- a global index of about 140 tables;
- one `events.db` plus a `meta.json` per session, which is the authoritative ledger;
- one database per workspace.

That layout forces a boot-time directory scan to reconcile the per-session files into the global index (`specs/compozy_reverse_spec.md` OBS-STO-001, OBS-DMN-006).

The reverse spec's §8.1 marks persistence as **simplify**: keep persist-before-publish, the single writer and gap-free replay, and drop the multi-file layout.

## Decision

Use **one SQLite file**, `<home>/harness.db`, opened with:
- the pure-Go driver `modernc.org/sqlite`;
- WAL mode, **`synchronous=FULL`**, `busy_timeout=5000`, `foreign_keys=ON`; on darwin also **`fullfsync=ON`** and **`checkpoint_fullfsync=ON`**.

With WAL and `synchronous=NORMAL`, SQLite documents that a committed transaction "might roll back following a power loss or system crash". After such a rollback, sequences already seen by followers would be reassigned to different events, which no cursor-based consumer can detect. `FULL` adds a WAL sync on every commit. On macOS a plain `fsync` does not reach stable storage, and only `F_FULLFSYNC` does (SQLite's `fullfsync` pragma, off by default).

Every event lives in one ordinary rowid table (`pos INTEGER PRIMARY KEY`) with `UNIQUE (stream, seq)`:
- `seq` is assigned per stream, as `MAX(seq)+1` inside a `BEGIN IMMEDIATE` transaction.
- All writes go through **one writer goroutine** for the whole database.
- A unique `id` (ULID) makes appends idempotent.
- `pos` gives a global commit order.

`WITHOUT ROWID` was rejected for this table. SQLite recommends it only for rows well under a twentieth of a page, and a local measurement (2,000 rows of 3 KB) showed every row spilling to overflow pages with `WITHOUT ROWID`, and none with the rowid layout.

Migrations are embedded, append-only goose SQL files from the first commit.

## Alternatives Considered

### Alternative 1: Compozy's layout (global index + one database per session)

- **Description**: a per-session `events.db` + `meta.json`, plus a global index.
- **Pros**: per-session files can be archived or deleted independently; write contention is spread across files.
- **Cons**: boot reconcile scan; three migration streams; cross-session queries need the index; more failure modes, such as an orphaned `meta.json`.
- **Why rejected**: a single local user does not reach the write volume that justifies sharding, and the reconcile machinery is the kind of incidental complexity the reverse spec says to skip.

### Alternative 2: Append-only JSONL files per stream

- **Description**: one file per stream, fsync on append, with the sequence equal to the line number.
- **Pros**: trivial to inspect with `tail`/`jq`; no database dependency.
- **Cons**: no transactions across a stream head and its metadata; idempotency needs a separate index; crash-truncated lines need repair logic; queries by type or time need full scans.
- **Why rejected**: it re-implements what SQLite already guarantees.

### Alternative 3: `mattn/go-sqlite3` (cgo)

- **Description**: the C SQLite library via cgo.
- **Pros**: the reference SQLite engine and the fastest driver.
- **Cons**: needs a C toolchain for every build and makes cross-compilation hard; Linux binaries are no longer fully static with `CGO_ENABLED=0`. (On macOS no Go binary is fully static, since the system library is always linked dynamically, so that is not a differentiator there.)
- **Why rejected**: Compozy ships on `modernc.org/sqlite`, and the throughput needed here is small.

## Consequences

### Positive

- Recovery after a crash is SQLite's own WAL recovery. No reconcile step exists.
- Cross-stream queries ("all events since T") are a single SQL statement when later features need them.
- One migration stream.

### Negative

- All appends serialize on one writer goroutine. Expected throughput is far beyond a single user's agent traffic, but a hot stream can delay another stream's appends by one transaction.
- Every commit pays a storage flush (an `F_FULLFSYNC` on macOS can take milliseconds). If session volume makes this visible, the writer can group-commit queued appends in one transaction without changing any contract.
- Deleting one session's history later means `DELETE … WHERE stream = ?` plus a `VACUUM`, not removing a file.

### Risks

- **Write amplification if session token streaming is stored chunk by chunk.** Mitigation, owned by `acp-sessions`: coalesce chunks before appending, as Compozy does with 25 ms / 256 KiB / 64-event windows (OBS-SES-007).
- **Database growth without retention.** Mitigation: retention is an explicit non-goal here and becomes a follow-up when session streams land.

## Implementation Notes

- Stream IDs match `^[a-z][A-Za-z0-9_.:-]{0,127}$`, so uppercase IDs such as ULIDs can be embedded. This feature uses `daemon`; later features use prefixes such as `session:<id>` and `loop:<run>`.
- Payloads must be valid JSON and at most 1 MiB per event; absent data is stored as `{}`.
- Times are fixed-width UTC with milliseconds and never decrease along commit order.
- The schema-ahead check runs on a read-only connection before any migration, because goose itself does not refuse a newer database.
